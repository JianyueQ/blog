# 用户类型隔离 - 开发文档

> 日期：2026-05-30
>
> 目标：在 `sys_user` 表中新增 `user_type` 字段，区分前台用户与后台用户，实现前后台登录隔离。前台用户只能在前台登录，后台用户可在前后台登录。管理员创建用户时可选择用户类型，并可修改已有用户的类型。

---

## 一、现状分析

### 1.1 当前问题

| # | 问题 | 说明 | 严重程度 |
|---|------|------|--------|
| 1 | 无用户类型区分 | `sys_user` 表没有字段区分前台/后台用户 | 高 |
| 2 | 登录无来源限制 | `validateLogin()` 仅校验密码和状态，不校验用户类型与登录来源的匹配关系 | 高 |
| 3 | 任意用户可登录后台 | 任何用户只要知道账号密码，即可通过后台登录页进入管理后台 | 高 |
| 4 | 自动注册用户无标记 | 邮箱注册、第三方OAuth登录自动创建的用户与管理员手动创建的用户没有区别 | 中 |
| 5 | 前台OAuth登录不查绑定表 | `authLogin()` 只通过 `username=uuid` 查找用户，不查 `sys_user_third_party` 绑定表（详见1.3） | 高 |
| 6 | 前台OAuth登录不创建绑定记录 | 自动创建用户后，未写入 `sys_user_third_party`，导致前后台绑定机制不一致 | 中 |

### 1.2 现有登录入口

| 入口 | 接口 | source 参数 | 说明 |
|------|------|-------------|------|
| 前台账号密码登录（blog-web） | `POST /auth/login` | `PC` | 前台用户登录 |
| 后台账号密码登录（blog-admin） | `POST /auth/login` | `ADMIN` | 后台管理员登录 |
| 前台第三方OAuth登录 | `GET /api/auth/callback/{source}` | — | 自动注册/登录，仅前台 |
| 后台第三方OAuth登录 | `GET /api/auth/callback/admin/{source}` | — | 需绑定关系，仅后台 |
| 前台邮箱注册 | `POST /api/email/register` | — | 自动创建前台用户 |
| 微信小程序登录 | `GET /api/wechat/appletLogin/{code}` | — | 自动创建前台用户 |
| 微信公众号登录 | 微信扫码 | — | 自动创建前台用户 |

### 1.3 Bug复现：后台用户绑定第三方账号后，前台OAuth登录创建重复账号

**复现步骤**：

1. 管理员（`sys_user.id=1, username="admin"`）在后台个人中心绑定 GitHub 账号
2. `sys_user_third_party` 表写入绑定记录：`{user_id: 1, third_party_type: "github", third_party_id: "github_uuid_123"}`
3. 同一 GitHub 账号在前台使用第三方登录
4. `authLogin()` 获取到 OAuth `uuid = "github_uuid_123"`
5. 执行查询 `SELECT * FROM sys_user WHERE username = 'github_uuid_123'` → **查不到**（管理员的 username 是 "admin"）
6. 自动创建了一个**新的前台用户**，`username = "github_uuid_123"`

**根因分析**：

前台 `authLogin()` 和后台 `adminAuthLogin()` 使用了**完全不同的用户查找策略**：

| 方法 | 查找方式 | 问题 |
|------|---------|------|
| `adminAuthLogin()` | 先查 `sys_user_third_party` 绑定表 → 再通过 `user_id` 查用户 | ✅ 正确 |
| `authLogin()` | 直接查 `sys_user WHERE username = uuid` | ❌ 不知道绑定表的存在 |

**附加问题**：前台 `authLogin()` 自动创建用户时，**不会创建 `sys_user_third_party` 绑定记录**。这意味着前台用户只能靠 `username = uuid` 来识别身份，缺少与后台一致的绑定管理机制。

### 1.4 关键代码现状

**登录验证（AuthServiceImpl.validateLogin）**：

```java
private static void validateLogin(LoginDTO loginDTO, SysUser user) {
    if (user == null) { throw new ServiceException("登录用户不存在"); }
    if (!BCrypt.checkpw(loginDTO.getPassword(), user.getPassword())) {
        throw new ServiceException("用户名或密码错误");
    }
    if (user.getStatus() != 1) { throw new ServiceException("账号已被禁用"); }
    if (user.getUsername().equals(Constants.TEST) && loginDTO.getSource().equalsIgnoreCase("PC")) {
        throw new ServiceException("演示用户不允许门户登录！");
    }
    // ❌ 没有用户类型校验
}
```

**后台新增用户（SysUserServiceImpl.add）**：

```java

    if (baseMapper.selectByUsername(user.getUsername()) != null) {
        throw new RuntimeException("用户名已存在");

}
```

## 二、设计方案

### 2.1 设计原则

| 原则 | 说明 |
|------|------|
| 最小改动 | 只新增一个字段，在所有用户创建点设置默认值，在登录验证处增加一个判断 |
| 向前兼容 | 存量用户默认设为后台用户（`user_type=1`），确保现有管理员不受影响 |
| 安全隔离 | 前台用户无论如何无法登录后台（账号密码、第三方OAuth均拦截） |
| 灵活管理 | 管理员可在后台修改用户类型，实现前台→后台的提升 |

### 2.2 用户类型定义

| 值 | 含义 | 前台登录 | 后台登录 | 创建方式 |
|----|------|---------|---------|---------|
| `0` | 前台用户 | ✅ 允许 | ❌ 禁止 | 前台注册、第三方OAuth自动创建、管理员手动创建 |
| `1` | 后台用户 | ✅ 允许 | ✅ 允许 | 管理员手动创建（默认）、管理员修改前台用户类型 |

> **为什么后台用户也能登录前台？** 管理员也是用户，可能需要在前台浏览、评论、管理内容。

### 2.3 用户创建场景与默认类型

| 场景 | 代码位置 | 默认 user_type | 说明 |
|------|---------|---------------|------|
| 管理员后台新增用户 | `SysUserServiceImpl.add()` | 由管理员选择，默认 `1`（后台用户） | 新增用户表单增加类型选择器 |
| 前台邮箱注册 | `AuthServiceImpl.register()` | `0`（前台用户） | 自动注册的都是前台用户 |
| 前台第三方OAuth登录（新建） | `AuthServiceImpl.authLogin()` | `0`（前台用户） | 首次授权自动创建 |
| 微信小程序登录（新建） | `AuthServiceImpl.appletLogin()` | `0`（前台用户） | 首次登录自动创建 |
| 微信公众号登录（新建） | `AuthServiceImpl.wechatLogin()` | `0`（前台用户） | 首次登录自动创建 |
| 存量用户数据迁移 | SQL ALTER | `1`（后台用户） | 保证现有用户不受影响 |

## 三、数据库变更

### 3.1 新增字段

```sql
-- 在 sys_user 表新增 user_type 字段
ALTER TABLE sys_user 
ADD COLUMN user_type TINYINT NOT NULL DEFAULT 1 
COMMENT '用户类型 0:前台用户 1:后台用户' 
AFTER status;
```

### 3.2 存量数据迁移

```sql
-- 将所有已有用户设为后台用户（向前兼容）
UPDATE sys_user SET user_type = 1 WHERE user_type IS NULL;
```

> **说明**：默认值设为 `1`（后台用户），这样在 `ALTER TABLE` 时所有存量记录自动填充为 `1`，无需额外执行 `UPDATE`。但建议显式执行一次确认。

### 3.3 字段设计说明

| 项目 | 说明 |
|------|------|
| 字段名 | `user_type` |
| 类型 | `TINYINT`（与 `status` 字段风格一致） |
| 默认值 | `1`（后台用户），确保兼容存量数据 |
| NOT NULL | 是，不允许为空 |
| 位置 | 放在 `status` 字段之后 |

```java
private static void validateLogin(LoginDTO loginDTO, SysUser user) {
    if (user == null) {
        throw new ServiceException("登录用户不存在");
    }
    if (!BCrypt.checkpw(loginDTO.getPassword(), user.getPassword())) {
        throw new ServiceException("用户名或密码错误");
    }
    if (user.getStatus() != 1) {
        throw new ServiceException("账号已被禁用");
    }
    // 前台用户禁止登录后台
    if ("ADMIN".equalsIgnoreCase(loginDTO.getSource()) 
            && user.getUserType() != null 
            && user.getUserType() == Constants.USER_TYPE_FRONT) {
        throw new ServiceException("前台用户不允许登录后台管理系统");
    }
    if (user.getUsername().equals(Constants.TEST) && loginDTO.getSource().equalsIgnoreCase("PC")) {
        throw new ServiceException("演示用户不允许门户登录！");
    }
}
```

### 4.5 用户自动创建场景 — 设置 `userType = 0`

以下场景需要在新建用户时显式设置 `userType(0)`：

#### (1) 邮箱注册 — `register()`

```java

        .username(dto.getEmail())
        .password(BCrypt.hashpw(dto.getPassword()))
        .nickname(dto.getNickname())
        .email(dto.getEmail())
        .avatar(avatar)
        .status(Constants.YES)
        .userType(Constants.USER_TYPE_FRONT)  // 新增
        .build();
```

#### (2) 前台第三方OAuth — `authLogin()`

前台OAuth登录需要**改造查找策略**，与后台保持一致：先查绑定表，再查 username，最后创建新用户。

```java
public void authLogin(AuthCallback callback, String source, HttpServletResponse response) {
    // ... 获取 OAuth 用户信息（不变）
    String uuid = jsonObject.get("uuid").toString();

    // ① 先查 sys_user_third_party 绑定表（新增）
    SysUserThirdParty binding = sysUserThirdPartyService.getByThirdParty(source, uuid);
    SysUser user = null;
    if (binding != null) {
        // 已绑定：通过绑定关系找到用户
        user = userMapper.selectById(binding.getUserId());
    }
    if (user == null) {
        // ② 再查 username = uuid（兼容历史数据：之前自动创建的用户）
        user = userMapper.selectOne(new LambdaQueryWrapper<SysUser>()
                .eq(SysUser::getUsername, uuid));
    }
    if (user == null) {
        // ③ 不存在：创建新用户 + 创建绑定记录
        user = SysUser.builder()
                .username(uuid)
                .password(UUID.randomUUID().toString())
                .loginType(source)
                .lastLoginTime(LocalDateTime.now())
                .ipLocation(ipSource)
                .ip(ipAddress)
                .status(Constants.YES)
                .userType(Constants.USER_TYPE_FRONT)  // 新增
                .nickname(source + "-" + getRandomString(6))
                .avatar(jsonObject.get("avatar").toString())
                .build();
        userMapper.insert(user);
        insertRole(user);
        // 创建绑定记录（新增）
        sysUserThirdPartyService.bind(user.getId(), source, uuid,
                jsonObject.containsKey("nickname") ? jsonObject.get("nickname").toString() : null,
                jsonObject.get("avatar").toString());
    }

    StpUtil.login(user.getId());
    response.sendRedirect(Constants.LOGIN_SUCCESS_URL + StpUtil.getTokenValue());
}
```

> **注意**：`bind()` 方法中有「该第三方账号已被其他用户绑定」的校验，但由于我们已在上方判断过 binding 不存在，所以不会冲突。如果存在并发问题，可考虑加锁或 catch `ServiceException`。

**查找策略对比**：

| 步骤 | 改造前（旧） | 改造后（新） |
|------|-------------|-------------|
| 1 | `SELECT * FROM sys_user WHERE username = uuid` | `SELECT * FROM sys_user_third_party WHERE type = source AND id = uuid` |
| 2 | 不存在 → 直接创建新用户 | 找到绑定 → 通过 user_id 查用户 |
| 3 | — | 未找到绑定 → `SELECT * FROM sys_user WHERE username = uuid`（兼容历史数据） |
| 4 | — | 仍不存在 → 创建新用户 + 创建绑定记录 |

### 4.7 前台OAuth登录绑定记录创建

**文件**：`mojian-auth/src/main/java/com/mojian/service/impl/AuthServiceImpl.java`

`authLogin()` 改造后，自动创建新用户时需同步创建 `sys_user_third_party` 绑定记录（已在4.5第(2)点中体现）。

此外，对于**已存在但无绑定记录的历史用户**（即之前通过 `username=uuid` 自动创建的用户），在登录成功后也应补建绑定记录：

```java
// 在找到用户（通过 username=uuid）但未找到绑定记录的情况下
if (binding == null && user != null) {
    try {
        sysUserThirdPartyService.bind(user.getId(), source, uuid,
                jsonObject.containsKey("nickname") ? jsonObject.get("nickname").toString() : null,
                jsonObject.containsKey("avatar") ? jsonObject.get("avatar").toString() : null);
    } catch (ServiceException e) {
        // 绑定已存在或冲突，忽略
        log.warn("补建绑定记录失败: {}", e.getMessage());
    }
}
```

## 六、安全隔离矩阵

下表总结所有登录场景下的隔离策略：

| 登录场景 | 前台用户 (userType=0) | 后台用户 (userType=1) |
|---------|---------------------|---------------------|
| 前台账号密码登录 (source=PC) | ✅ 允许 | ✅ 允许 |
| 后台账号密码登录 (source=ADMIN) | ❌ 拒绝 | ✅ 允许 |
| 前台第三方OAuth | ✅ 允许 | ✅ 允许 |
| 后台第三方OAuth | ❌ 拒绝 | ✅ 允许 |
| 前台邮箱注册 | ✅ 创建为前台用户 | — |
| 微信小程序/公众号登录 | ✅ 创建为前台用户 | ✅ 允许 |

### 拦截点汇总

| 拦截点 | 代码位置 | 拦截方式 |
|--------|---------|---------|
| 后台账号密码登录 | `validateLogin()` | 检查 `source=ADMIN` + `userType=0` → 抛异常 |
| 后台第三方OAuth登录 | `adminAuthLogin()` | 检查 `userType=0` → 重定向带 `?error=front_user` |

| `ALTER TABLE sys_user ADD COLUMN user_type ...` | 新增字段 |

## 八、实施顺序

1. **数据库** → 执行 `ALTER TABLE` 添加字段
2. **实体类** → `SysUser.java` 添加 `userType` 字段
3. **常量** → `Constants.java` 添加类型常量
4. **登录校验** → `AuthServiceImpl.validateLogin()` 增加类型拦截
5. **后台OAuth校验** → `AuthServiceImpl.adminAuthLogin()` 增加类型拦截
6. **前台OAuth改造** → `AuthServiceImpl.authLogin()` 改造查找策略 + 创建绑定记录 + 设置 userType
7. **其他自动创建** → `register()` / `appletLogin()` / `wechatLogin()` 设置 `userType(0)`
8. **后台新增** → `SysUserServiceImpl.add()` 增加默认值
9. **前端页面** → 用户管理表单/列表/搜索
10. **前端登录** → 错误提示映射

## 九、替代方案对比

在确定当前方案前，考虑过以下替代方案：

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|---------|
| **A. sys_user 加 user_type 字段** | 简单直接、查询方便、改动最小 | 需要改实体类 | ✅ 采用 |
| B. 通过角色判断（有 admin 角色 = 后台用户） | 不改表结构 | 耦合角色系统；查询需 JOIN；语义不清晰；普通角色用户也想进后台 | ❌ |
| C. 新建 sys_user_type 关联表 | 扩展性强 | 过度设计；增加查询复杂度 | ❌ |
| D. Sa-Token 多账号体系（StpUserUtil / StpAdminUtil） | 天然隔离 | 改动巨大；需重构所有登录逻辑；不兼容现有架构 | ❌ |

**结论**：方案 A 在改动量、清晰度、安全性上取得最佳平衡。

## 十、第三方平台 UUID 特性分析

不同第三方平台返回的 UUID 在前后台 OAuth 应用间是否一致，直接影响绑定表的复用效果：

| 平台 | UUID 特性 | 前后台 OAuth 返回是否相同 | 影响 |
|------|----------|------------------------|------|
| **GitHub** | 全局用户ID（平台级别） | ✅ 相同 | 前台登录可复用后台绑定 |
| **Gitee** | 全局用户ID（平台级别） | ✅ 相同 | 前台登录可复用后台绑定 |
| **QQ** | 应用级别 OpenID（每个 OAuth 应用独立） | ❌ 不同 | 前后台各自独立用户，绑定无法复用 |

> **结论**：对于 GitHub / Gitee，前后台共享绑定表可以正确识别同一用户。对于 QQ，由于前后台是不同的 OAuth 应用，返回的 OpenID 不同，绑定表无法跨应用匹配，前后台会各自创建独立用户——这是 QQ 平台的限制，无法通过代码规避。

## 十一、完整改动总览（含Bug修复）

相比初版设计，新增了以下改动：

| 改动 | 说明 |
|------|------|
| `authLogin()` 查找策略改造 | 先查 `sys_user_third_party` → 再查 `username=uuid` → 最后创建新用户 |
| `authLogin()` 创建绑定记录 | 新建用户时同步写入 `sys_user_third_party` |
| `authLogin()` 补建历史绑定 | 已存在但无绑定记录的历史用户，补建绑定关系 |

这使得前台和后台的第三方登录机制完全一致，解决了「后台绑定后前台创建重复账号」的Bug。
